# Матрица трассируемости

Файл: `<feature>_rtm.md` · Владелец: business-analyst

## Назначение

Матрица трассируемости показывает, как каждая бизнес-цель доходит до критериев приёмки, требований, системных решений и тестов, и где эта цепочка рвётся. business-analyst собирает её по ID из всех артефактов каталога, включая артефакты system-analyst, и меняет только `_rtm.md`. Матрица производна: источником истины для каждого ID остаётся артефакт его владельца.

## Входы

- Все артефакты каталога `docs/analysis/<feature>/`: `_business-case.md`, `_user-story.md`, `_brd.md`, `_use-case.md`, `_gap-analysis.md`, `_process-to-be.md`, `_backend.md`, `_nfr.md`, `_openapi.yaml`, `_asyncapi.yaml`.
- Тесты и тест-кейсы в файлах проекта, которые ссылаются на ID требований.
- ID собираются grep'ом по шаблонам `BG-[0-9]+`, `US-[0-9]+`, `AC-US-[0-9]+-[0-9]+`, `BR-[0-9]+`, `RULE-[0-9]+`, `UC-[0-9]+`, `CHG-[0-9]+`, `FR-[0-9]+`, `NFR-[0-9]+`. Операции берутся из `operationId` в `_openapi.yaml`, каналы — из `channels` в `_asyncapi.yaml`, связь `FR` с операцией или каналом — из `_backend.md`.
- Факты, которых нет в источниках, запрашиваются у пользователя одним сообщением:
  1. где лежат тесты или тест-кейсы и как они ссылаются на требования;
  2. какие разрывы покрытия уже признаны допустимыми, кем и почему.
- `[GAP]` в матрицу не ставится: пустая ячейка означает «ещё не создано». Неясная связь оформляется вопросом `Q-n` к владельцу артефакта, в котором эта связь должна быть записана.

## Правила

1. Строка матрицы соответствует элементу нижнего уровня: `AC`, а для `BR`, у которого нет связанных историй, — самому `BR`. Элементы верхних уровней повторяются в каждой своей строке, чтобы строку можно было прочитать отдельно.
2. Несколько ID одного типа в ячейке перечисляются через запятую.
3. Ячейка содержит ID, который существует в файле владельца, или остаётся пустой. Пустая ячейка означает «ещё не создано».
4. Матрица отражает только связи, записанные в артефактах: `AC` → `US` из user-story, `BR` → `US`, `UC`, `P-n` из BRD, `CHG` → `BR`, `US` из Gap-анализа, `FR` → источник и операция из backend, `NFR` → `BR` из NFR. Связь, которой нет ни в одном артефакте, оформляется `Q-n` к владельцу артефакта, где она должна быть.
5. Колонка «Покрытие»: «полное» — заполнены все колонки, для которых артефакты существуют; «частичное» — перечислены пустые колонки при существующем артефакте; «разрыв принят» — строка есть в таблице «Принятые разрывы».
6. Разрыв, который не планируется закрывать, записывается в «Принятые разрывы» с причиной и ролью, которая его приняла, по источнику.
7. Колонка «Тест» заполняется ID или путями тестов из файлов проекта.
8. Каждая проверка покрытия выполняется при каждой сборке. Проверка без находок получает `0` и «—».
9. Матрица пересобирается целиком при каждом обновлении; таблица источников и версия обновляются вместе с ней.

## Чеклист качества

- [ ] Таблица источников перечисляет каждый артефакт из списка входов с версией и статусом, отсутствующие отмечены.
- [ ] Каждый `AC` из `_user-story.md` есть в матрице.
- [ ] Каждый `BR` из `_brd.md` есть хотя бы в одной строке матрицы.
- [ ] Каждый ID в матрице существует в файле владельца.
- [ ] Каждая связь в строке подтверждается ссылкой в одном из артефактов.
- [ ] Ячейки матрицы содержат только ID или пусты; неясные связи вынесены в `Q-n`.
- [ ] Колонка «Покрытие» заполнена в каждой строке и согласована с пустыми ячейками.
- [ ] Каждая строка со статусом «разрыв принят» есть в таблице «Принятые разрывы» с причиной и ролью, которая его приняла.
- [ ] Все шесть проверок покрытия выполнены, у каждой указаны число, элементы и адресат.
- [ ] Каждый элемент из таблицы проверок виден в матрице как пустая ячейка или отсутствующая строка.
- [ ] Каждый `Q-n` имеет адресата.

# Типы заметок, шаблоны и frontmatter

Шаблоны лежат в `_Система/1. Шаблоны/`. Все политики этого файла применяются ко всем скиллам и ручным правкам, создающим или редактирующим заметки.

## Шаблоны по типам заметок

Полный выбор «ситуация → шаблон» — таблица в навыке `/note-templates`. Неочевидные: `Шаблон предмета.md` — MOC дисциплины МТИ (`Предмет X.md`: breadcrumb ВПО/СПО, LMS-ссылка в `links`, опциональный «Учебный модуль»); `Шаблон семестра.md` — семестр МТИ (`<ОВБИм|ОДКИПо> Semester N – YYYY.md`, тег `semester`: предметы с формой контроля, breadcrumb между семестрами и хабом).

## Стандартные поля frontmatter

| Ключ | Тип | Описание | Когда использовать |
|------|-----|----------|--------------------|
| `aliases` | list | Альтернативные названия | Всегда |
| `tags` | list | Теги заметки | Всегда |
| `created` | string | Дата создания ISO `YYYY-MM-DDTHH:mm` | Всегда (Templater) |
| `status` | string | `Todo`, `WIP`, `Done` | Проекты/Посты |
| `deadline` | string | Дедлайн как wikilink `"[[2026-03-05]]"` | Проекты |
| `up` | list | Родительские заметки | Всегда |
| `down` | list | Дочерние заметки | Всегда |
| `links` | list | Ссылки на веб-ресурсы | Всегда |
| `other` | list | Горизонтальные связи | Всегда |
| `category` | string | «Полка» источника — всегда wikilink на карту/топик | Тезисы по источнику |
| `summary` | string | 1–3 предложения сути на русском; plain text | Концепты, литературные заметки, тезисы, синтезы, эссе, MOC |
| `description` | string | 1–3 предложения сути проекта на русском; plain text | Только проекты (`#project`) |
| `confidence` | string | `high`, `medium`, `low` | Концепты, литературные заметки, синтезы |
| `sources` | list | Исходные заметки/документы | Литературные заметки, синтезы |
| `contradicts` | list | Противоречащие заметки | Концепты, литературные заметки, синтезы, эссе |
| `contribution` | string | Чем человек силён, что даёт | Профили людей (`#person`) |
| `ask` | string | Что ищет, чем ему быть полезным | Профили людей (`#person`) |
| `next_step` | string | Следующий шаг в контакте; пусто = шага нет | Профили людей (`#person`) |
| `ai_generated` | bool | `true` = сгенерировано скиллом; отсутствие = автор | Заметки, созданные скиллом (см. политику) |

Общие правила: сохраняй все существующие ключи, не изобретай новые без причины; не меняй формат существующих значений (список не превращай в строку); новые поля — только консистентные с заметками того же типа; **`sources` никогда не очищай, только добавляй**.

### Политика: строковые значения всегда в двойных кавычках

**Любое однострочное строковое значение во frontmatter оборачивается в двойные кавычки** (`summary`, `description`, `category`, `date`, `deadline`, `contribution`, `ask`, `next_step`, `speaker`…). Исключение — технические скаляры без пробелов и знаков препинания: `status: Done`, `created: 2026-07-30T16:55`. Незакавыченное `: ` ломает YAML и отображение всей заметки; кавычки заодно закрывают спецсимволы (`#`, `&`, `*`, `|`, `>`, `[`, `{`) в начале значения и краевые пробелы.

- Двойные кавычки, не одинарные; двойную кавычку внутри текста заменяй на «ёлочки».
- Многострочные значения не используем: `summary` — 1–3 предложения одной строкой.
- Списки: элементы-wikilinks закавычены по конвенции, URL можно без кавычек.
- **Отступ элемента списка — ровно два пробела**; нулевой отступ рвёт отображение так же, как двоеточие.

**Проверка:** после правки frontmatter — `ruby .agents/scripts/check_frontmatter.rb .`, ноль находок обязателен. При расхождении со SKILL `obsidian-add-summary` главнее правило здесь.

### Политика: карточка контакта (contribution / ask / next_step)

Профили людей (`#person`, `02. Сферы/01. Люди/`) несут три опциональных строковых поля.

- Все три — plain text без wikilinks; связи живут в теле (`## Совместные контексты`) и в `up`/`other`.
- Поле «последняя встреча» не ведём — его выводит Bases-вью «Когда вспоминал».
- `next_step`: закрыл шаг — очисти или впиши следующий; пустая строка = осознанное «шага нет».
- Не дозаполняются массово — только при живом касании профиля (встреча, договорённость).
- **Семейные профили** (`up: [[Моя семья]]`) — поля не заполняются. **Справочные фигуры** (философы, писатели без контакта) — вне контура карточки целиком.

### Политика: метаданные vs граф

`created` — метаданное, не отношение: ISO-строка без кавычек и без wikilink, ставит Templater, после создания не обновляется. Wikilink на дневник в `created` запрещён — дневная заметка не должна становиться искусственным хабом графа.

- Заметка *вышла* из конкретного дня — ссылка на дневник в `sources` или `up`, не в `created`.
- **Поле `modified` не вводим** — CLI-правки вне Obsidian делают его враньём.

**`date`** в шаблонах ADR, инцидента, лекции, встречи — дата события, не создания заметки (wikilink на дневной файл допустим). Принадлежит только заметке-событию: выделенные из события атомарки `date` не копируют — связь уже выражена через `up`/`sources` (и `discipline` у учебных), у атомарки только `created`.

### Политика: литературные источники в up + sources (вариант Б)

Литературный источник — и тематический родитель, и источник: ссылка на него идёт **и в `up`, и в `sources`**: `up: ["[[Книга – Проект Феникс]]", "[[DevOps]]"]` + `sources: ["[[Книга – Проект Феникс]]"]`.

- Источник попал в `up` — обязательно продублируй в `sources`; при обновлении любой стороны следи за синхронностью.
- Исключение: **навигационные MOC-индексы** (`Книжная полка`, `Статьи`, `Видео`, `Конференция` и аналогичные с `MapOfContent`) — родители, не источники: в `sources` не дублируются.

История миграции — [[Литературные источники остаются в up и дублируются в sources]].

### Политика: contradicts как типизированное ребро графа

Фиксируем противоречие дважды: callout `> [!warning]` в тексте (объяснение «в чём именно») + поле `contradicts` во frontmatter (сам факт, для запросов по графу).

- **Двустороннее поле:** если `A` противоречит `B`, ссылка обязана быть в обеих заметках.
- Применяется: концепты/мысли, литературные заметки, синтезы, эссе. Не применяется: дневник, проекты, профили людей, встречи/конференции.
- Не путать с `other` («рядом по теме» vs «взаимоисключающее») и с `confidence: low` (оценка одной заметки vs отношение к другим).
- Фиксировать: при ингесте; при health check (чинить односторонние связи, предлагать синтез); при опровержении старой заметки — сначала противоречие, потом решение (обновить, синтез, открытый вопрос).

### Политика: ai_generated как маркер авторства

`ai_generated` — маркер прозрачности: через год отличить своё от сгенерированного иначе невозможно.

- `true` — содержимое создано скиллом без существенной ручной правки; **отсутствие поля** = написано автором (дефолт, `false` без причины не ставим).
- Автор существенно переписал черновик — удаляй поле; гибриды (каркас от агента, детали от автора) держат `true`, пока автор не считает заметку своей.
- Ставят скиллы, **создающие** заметки: `obsidian-ingest`, `obsidian-split-note`, `obsidian-note-critic`, `book-highlights-processor`, `obsidian-untangle-knot`. НЕ ставят: авторские и журнальные шаблоны, `obsidian-refactor-inbox`, `obsidian-enrich-note`, `obsidian-daily-append`, `obsidian-journal-review`, `humanize-article`.
- `obsidian-split-note` — граничный случай: текст авторский, но агент переформулирует, именует и собирает frontmatter — ставим `true`.
- Рождается такая заметка в `00. Входящие/` с `#review` (`workflows.md`); после ревью `#review` снимается, `ai_generated` остаётся до переписывания автором.

### Политика: down — навигация, не реестр потомков

- **Смысловое перечисление детей в теле** (`## Ключевые идеи`, `## Список лекций и ИМ`, `## Ключевые заметки`, `## Посетил следующие доклады`) в `down` не дублируем — тело и есть источник правды, `down` пуст или держит крупные узлы.
- **Связь допустимо оставлять односторонней:** у дочерней заметки `up` и `sources` на источник обязательны, обратная ссылка — нет (её показывают backlinks и Bases).
- **Курируемые вручную списки в теле чужой заметки без спроса не дописываем** — предложи и дождись ответа.
- Когда `down` всё же заполняем (MOC, под-MOC) — держим там узлы, а не листья.

### Политика: sources обязателен для ai_generated

Заметка с `ai_generated: true` и пустым `sources` — дефект: у утверждения нет ни автора, ни источника.

**Источником считается:** заметка-источник в базе (книга, статья, видео, доклад, литературная заметка); внешний URL; заметка дневника; артефакт хранилища (холст, `.base`, скрипт, конспект); файл правил `.agents/rules/*`, если агент пересказывает принятые автором правила.

- `sources` заполняется в момент создания заметки, а не «потом при ревью».
- **Память модели источником не является** — если ничего из списка не подходит, содержательная заметка не создаётся.
- **Заглушка под битую ссылку — законное исключение:** `sources: []` ставится осознанно + строка в теле, что это справочное определение, не авторское знание.
- Наткнулся — восстанови источник или пометь как заглушку, молча не оставляй; проверка входит в health check (`workflows.md`).

### Политика: summary как сигнал сути для агентов

`summary` — 1–3 коротких предложения сути на русском: агент и Bases-таблица понимают релевантность без чтения тела. Формат: строка plain text без wikilinks, markdown и переносов; термины на английском; claim-based, не пересказ структуры («в заметке рассматривается…» запрещено).

| Тип | `summary` | Стиль |
|-----|-----------|-------|
| Концепт / мысль (`#concept`, `#thought`) | Обязателен | Claim: суть утверждения |
| Литературная заметка (`#literature-note`) | Обязателен | Главный тезис источника и чем полезен |
| Тезисы по книге/статье/видео/докладу | Обязателен | Центральная идея + предложение об охвате |
| Синтез (`#synthesis`) | Обязателен | Вывод сравнения: что выбрать и когда |
| Эссе | Обязателен | Главная мысль текста |
| MOC (`#MapOfContent`) | Обязателен | Не claim: какие темы собирает и для какой задачи |
| Проекты (`#project`) | Не ставится — вместо него `description` | См. политику `description` ниже |
| Остальные контейнерные (люди, встречи, конференции, инциденты) и журнальные | Не ставится | Суть видна из имени, статусов, даты |

- **При существенной правке тела обновляй `summary` в той же сессии** — врущий хуже отсутствующего.
- До-генерация `summary` в существующей авторской заметке НЕ ставит `ai_generated`.
- Не ужимается в 3 предложения — в заметке несколько идей: кандидат на `#needs-split` ([[Обогащение базы знаний для агентного взаимодействия]]).
- **Точные числа и величины не выносим — только смысл**; конкретика живёт в теле рядом с источником.
- Значение всегда в двойных кавычках.
- Только русский, `summary_en` не вводим: embedding-модели кросс-языковые, второе поле — гарантированный рассинхрон.
- Батч-заполнение — скилл `obsidian-add-summary`.

### Политика: description как сигнал сути проекта

**`description` принадлежит только проектным заметкам (`#project`)** — по наличию поля проект отличается от всех остальных типов. Заметка сути у проекта одна: либо `description`, либо ничего; `summary` в проекте не заводим, а найденный — переименовываем в `description`.

Формат — тот же, что у `summary`: 1–3 коротких предложения на русском, plain text без wikilinks, markdown и переносов, значение в двойных кавычках, термины на английском. Содержание другое: не claim, а **что делаем и какой результат считается готовым**; если проект закрыт или заброшен — это тоже часть описания.

- Обязателен на каждой заметке с тегом `#project`, включая уехавшие в `04. Архив/`.
- Заполняется при создании проекта и обновляется, когда меняется суть или статус работы, — врущий `description` хуже отсутствующего.
- **Точные числа, суммы и даты не выносим** — конкретика живёт в теле рядом с фактурой.
- Из него собирается колонка «Суть» в Bases-срезах [[Карта проектов]]: карта ручных списков не ведёт, поэтому пустое поле означает пустую ячейку в навигации.
- Заметка в `01. Проекты/` без тега `#project` (черновик, встреча, попавшая в папку заметка) поля не получает — сначала решается её тип.

Обоснование разделения: `summary` работает как сигнал релевантности при семантическом поиске по знаниям, а проект — контейнер работы, а не утверждение. Отдельное имя поля не даёт им смешаться ни в Bases-срезах, ни в выдаче агента.

### Политика: category как ссылка на карту или топик

`category` — тематическая «полка» источника-тезиса, **обязана быть wikilink** на карту (`#MapOfContent`) или топик (`#topics`): plain text не резолвится в графе.

1. **Существующая более общая карта/топик имеет приоритет.** Занятые полки показывает `grep -rh "^category:" "03. Ресурсы/"`; предпочитай более общую из подходящих.
2. **Одно значение — одна полка:** строка с одной ссылкой, темы через `/` или запятые не склеиваем; более узкие связи — в `up`/`other`.
3. **Ничего не подходит — ссылка-заглушка**, не текст, именем по `file-naming.md`; при 5+ заметках заглушку материализуют в карту (навык `/knowledge-structures`).
4. **Plain text оставлять нельзя** — при любой обработке конвертируй в wikilink на существующую карту/топик или заглушку.

**Не путать с `up`:** у тезисов `up` — навигационный MOC-индекс источников (`[[Видео]]`, `[[Книжная полка]]`), `category` — тематическая рубрика («оно про SRE»). `obsidian-untangle-knot` поле `category` при перепривязке ссылок не трогает.

## Уровни достоверности (confidence)

| Уровень | Значение |
|---------|----------|
| `high` | Несколько подтверждающих источников, проверена на практике |
| `medium` | Подкреплена источниками, но мало примеров или единственный источник |
| `low` | Единичное упоминание, анекдотично или спекулятивно — требует проверки |

- Обязателен для типов: Концепт, Литературная заметка, Синтез
- Из единственного источника — по умолчанию `medium`; идея теоретическая или не уверен — `low` с пометкой в тексте
- При обновлении новыми источниками — повышай уровень и обновляй `sources`
- Не ставь `high` без минимум двух независимых источников или личного опыта

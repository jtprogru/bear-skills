# Runbook — гайд по секциям

Этот файл — подробный разбор каждой секции v1-шаблона `runbook.yaml`. SKILL.md задаёт верхнеуровневые правила; здесь — что писать и чего не писать в каждой секции, с примерами.

Общее правило: **прескриптивно, в императиве настоящего времени, идемпотентно**. Если ты не можешь переформулировать что-то в инструкцию для будущего читателя — это не место в runbook'е.

---

## `symptoms` — Симптомы (Symptoms)

**Цель**: чтобы дежурный, увидев алерт или paged-страницу, за 10 секунд понял «да, это про мой случай».

**Что писать**:

- Имя сработавшего алерта (точно так, как в Alertmanager).
- Panel дашборда, который показывает аномалию (URL).
- Конкретный паттерн в логах (regex или фразу).
- Юзер-визиблый эффект (что отвечает API, что видит клиент в UI).

**Что НЕ писать**:

- «Пользователь жалуется на медленный ответ» — это симптом для incident-доска, не для runbook. Runbook не активируется через жалобы — он активируется через алерт.
- Перечисление всех возможных симптомов «когда-то и где-то» — оставь самые надёжные сигналы, которые однозначно указывают на этот failure mode.

**Пример (хороший)**:

```markdown
- Алерт `DRBDStalePrimary` (severity: page).
- На дашборде [`drbd-overview`](https://grafana/d/drbd) больше одной ноды с `drbd_resource_role="Primary"` для одного ресурса.
- В `journalctl -u drbd` повторяется `Refusing to be Primary: device in use`.
- VM на затронутом ресурсе либо зависает при `virsh start`, либо отвечает с I/O errors.
```

**Пример (плохой)**:

```markdown
- Диски тормозят
- Пользователи жалуются
```

## `severity_slo_impact` — Тяжесть и влияние на SLO

**Цель**: помочь дежурному решить: будить ли сейчас остальных, или дотерпит до утра.

**Что писать**:

- Какой SLO/SLI горит. Точное имя SLI из `slo-<service>.md` или из конфига.
- Скорость сгорания бюджета: «при текущей частоте — час до Yellow, четыре до Orange».
- Кого ещё затрагивает: зависимые сервисы, типы клиентов.
- Решение по severity-уровню как **функция от метрики**, а не константа: «SEV-1 если SLI < 99% последние 15 минут, SEV-2 если 99–99.5%».
- Эскалация: кого будить, если за N минут не починится.

**Что НЕ писать**:

- «Critical». Слово без референта.
- Фиксированное severity для всех случаев — не у каждого срабатывания этого алерта одинаковый impact.

**Пример**:

```markdown
- **SLI под угрозой:** `csi_pvc_create_success_rate` (target: 99.5% / 30d).
- **Скорость сгорания:** при 0% success rate бюджет 30d сгорает за ~4 часа.
- **SEV:** SEV-1 если в течение 15 минут success rate < 80%; SEV-2 при 80–99%; SEV-3 при > 99% с эпизодическими провалами.
- **Зависимости:** новые VM не стартуют, существующие VM работают (deg, не outage).
- **Эскалация:** если за 30 минут после mitigation не закрылось — SRE Lead.
```

## `diagnose` — Диагностика

**Цель**: за минимум команд выяснить, **тот ли это failure mode** и **на какой ноде / сервисе**.

**Что писать**:

- **Упорядоченный** список проверок, от самой быстрой и широкой к более глубоким и узким.
- Каждая проверка — **команда** (`kubectl …`, `psql …`, PromQL-запрос, ссылка на дашборд с предзаполненным фильтром).
- **Ожидаемый** и **аномальный** вывод. «Если видишь X — это нормально; если Y — этот случай.»
- Decision tree: «если на шаге 2 видишь A → переходи к Mitigate; если B → это другой failure mode, см. [other-runbook.md]».

**Что НЕ писать**:

- «Проверь логи». Какие логи. Какой regex. Какой паттерн искать.
- «Открой Grafana». Какой dashboard. Какая panel.
- Без копи-пастабельной команды diagnose-шаг бесполезен.

**Пример**:

```markdown
1. **Подтверди, что Primary действительно дублирующийся:**

   ```bash
   for node in $(kubectl get nodes -o name); do
     ssh ${node#node/} 'drbdadm status | grep -E "^[a-z].*Primary"'
   done
   ```

   - **Ожидаемо**: ровно одна нода в выводе для каждого ресурса.
   - **Аномально (этот runbook)**: две и более ноды Primary для одного ресурса.
   - **Аномально (другой случай)**: одна нода `StandAlone` — это [split-brain runbook](split-brain-resolution.md), не этот.

2. **Проверь, какая нода реально держит VM:**

   ```bash
   kubectl get vm -A -o wide | grep <resource>
   ```

   `NODE` колонка = нода с легальным Primary. Остальные Primary — stale.

3. **Подтверди отсутствие активных I/O на stale-ноде:**

   ```bash
   ssh <stale-node> 'lsof /dev/drbd<N> 2>/dev/null'
   ```

   Должно быть пусто. Если не пусто — **не демоути**, эскалируй (см. After the fact).
```

## `mitigate` — Смягчение

**Цель**: остановить кровотечение и вернуть систему в рабочее состояние **минимальным**, **идемпотентным**, **безопасным** набором шагов.

**Что писать**:

- **Упорядоченные** шаги. Первый — самый короткий путь к stop-the-bleeding (rollback, drain, failover, restart). Root cause — потом.
- Каждый шаг — **команда** + что **verify** после.
- **Маркируй рискованные шаги**: `> ⚠️ Перед выполнением убедись, что …`.
- **Идемпотентность**: повторное выполнение шага должно быть безвредным. Если нет — явно пометь `> ⚠️ Выполнять ровно один раз`.
- Если есть несколько путей mitigation (быстрый-но-грязный vs медленный-но-чистый) — оба, с критерием выбора.

**Что НЕ писать**:

- Расследование root cause. Это после mitigation, на холодную голову.
- «Перезапусти что-нибудь». Конкретный объект и команда.
- Шаги без verify. Каждый шаг должен говорить «как понять, что сработало».
- Шаги, которые могут уронить ещё что-то, без явного `> ⚠️`.

**Пример**:

```markdown
> ⚠️ Перед каждым demote-шагом убедись, что на ноде **нет работающей VM**, использующей ресурс. `virsh list --all | grep <resource>` должен быть пустым.

1. **Demote stale Primary** (идемпотентно):

   ```bash
   ssh <stale-node> 'drbdadm secondary <resource>'
   ```

   Verify: `ssh <stale-node> 'drbdadm role <resource>'` возвращает `Secondary`.

2. **Подтверди, что в кластере остался ровно один Primary**:

   ```bash
   for node in $(kubectl get nodes -o name); do
     ssh ${node#node/} 'drbdadm role <resource>'
   done | sort -u
   ```

   Должно быть две строки: `Primary` (одна) и `Secondary` (остальные).

3. **Перезапусти зависшую VM, если нужно**:

   ```bash
   virsh reset <vm>   # на ноде с легальным Primary
   ```

   > ⚠️ `virsh reset` — hard reset, без graceful shutdown. Использовать только если VM не отвечает.
```

## `verify` — Проверка

**Цель**: дать дежурному конкретный чек-лист, по которому он скажет «всё, можно отлогиниться».

**Что писать**:

- Чек-лист `- [ ]` с **конкретными** критериями.
- Конкретные **метрики и пороги**: «p99 < 300ms», «error rate < 0.1%», «нет повторных срабатываний 15 минут».
- Проверка отсутствия **побочных эффектов**: «зависимый сервис X не залит ретраями».

**Что НЕ писать**:

- «Всё ок». Что значит «ок».
- «Алерт погас» как единственный критерий — алерт может погаснуть на коротком окне, потом сработать снова.

**Пример**:

```markdown
- [ ] Алерт `DRBDStalePrimary` погас в Alertmanager.
- [ ] В `drbdadm status` ровно один Primary для каждого ресурса (см. команду в Diagnose шаг 1).
- [ ] Метрика `csi_pvc_create_success_rate{service="linstor"}` ≥ 99% за последние 5 минут (PromQL: ...).
- [ ] За 15 минут с момента mitigation повторных срабатываний `DRBDStalePrimary` нет.
- [ ] Зависимые сервисы (`kubevirt-controller`, `csi-controller`) не залиты ретраями: error rate < 1%.
```

## `after_the_fact` — Постфактум

**Цель**: переключить дежурного с «потушил пожар» на «теперь не забудь».

**Что писать**:

- Триггер для постмортема: при каком SEV-уровне обязателен постмортем (`SEV ≥ 2` — типично).
- Команда для скаффолда: `srekit postmortem -T "<копия title runbook'а>" --severity SEV-N --owner "<role>"`.
- Напоминание обновить **этот** runbook: «если в этот раз что-то удивило — добавь в Symptoms / Diagnose / Mitigate, чтобы следующий on-call не наступил на те же грабли».
- Куда заводить тикеты на root-cause фикс (если этот runbook — про симптом, а не про root cause).

**Что НЕ писать**:

- «Сделай постмортем» без сценария — заводится ли он всегда или только при критичном severity.
- Конкретные action items этого инцидента — это в постмортем, не в runbook.

**Пример**:

```markdown
- Если SEV ≥ 2 или mitigation занял > 30 минут — заводим постмортем:

  ```bash
  srekit postmortem -T "DRBD stale primary — <дата>" --severity SEV-N --owner "Storage owner"
  ```

- Если в этот раз что-то удивило (новый сценарий возникновения, неработающая команда из этого runbook'а, побочный эффект, не упомянутый в Verify) — **обнови этот runbook сразу же**, не откладывая.
- Root-cause фикс (избавиться от stale Primary как такового, а не лечить симптом) — тикет в [storage-team backlog](<GAP: ссылка>).
```

## `references` — Ссылки

**Цель**: дать дежурному пути в смежные документы, не дублируя их содержимое.

**Что писать**:

- Файл с определением алерта (`prometheus/alerts/<file>.yaml`).
- Дашборд (с URL).
- Родственные runbook'и (близкие failure modes).
- Прошлые постмортемы по этому же failure mode — особенно полезно для исторического контекста и подтверждения, что runbook реально работает на эту проблему.
- Код сервиса (директория в монорепо).
- SLO-документ.

**Что НЕ писать**:

- Битые ссылки. Если не уверен в URL — GAP-маркер.
- Дублирование содержимого из других runbook'ов / wiki.

**Пример**:

```markdown
- Алерт: [`prometheus/alerts/drbd.yaml`](../../prometheus/alerts/drbd.yaml) — `DRBDStalePrimary`.
- Дашборд: [drbd-overview](https://grafana/d/drbd).
- Родственные runbook'и:
  - [`split-brain-resolution.md`](split-brain-resolution.md) — когда нода в `StandAlone`.
  - [`frozen-synctarget.md`](frozen-synctarget.md) — когда SyncTarget завис.
- Прошлые постмортемы по тому же failure mode:
  - [`postmortem-2026-06-03-disk-50gb-create-hang.md`](../../incidents/postmortem-2026-06-03-disk-50gb-create-hang.md)
- Код: [`internal/storage/drbd/`](../../internal/storage/drbd/).
- SLO: [`docs/slo/slo-linstor.md`](../../docs/slo/slo-linstor.md).
```

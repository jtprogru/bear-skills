# Рабочие процессы

## Протокол «план → подтверждение → действие»

Применяется во всех скиллах, которые создают/перемещают/удаляют файлы пачкой: `obsidian-ingest`, `obsidian-split-note`, `obsidian-refactor-inbox`, `obsidian-note-critic` (когда создаёт ревью-заметку).

1. **План.** Перед пачкой изменений покажи структурированный список: что создать, что обновить, куда переместить, что удалить. Кратко (1 строка на пункт), с целевыми путями и тегами.
2. **Подтверждение.** Дождись подтверждения пользователя. Исключение: пользователь явно сказал «делай сразу», «без подтверждения», «погнали», или скилл обрабатывает один файл с очевидным результатом.
3. **Действие.** Порядок: создание новых файлов → обновление существующих → перемещение → удаление/архивация.
4. **Отчёт.** Краткая сводка: что создано, что обновлено, что осталось под вопросом.

Если по ходу план меняется (нашлась существующая заметка вместо создания новой, кейс не подходит под шаблон) — остановись, обнови план, спроси.

## Новые заметки рождаются во входящих

**Любую новую заметку, которую создаёт агент или скилл, кладём в `00. Входящие/` — не в целевую папку PARA.** Это касается атомарок, концептов, литературных заметок, тезисов, синтезов, MOC и под-MOC, профилей людей, ревью-заметок, черновиков постов — всего, что рождается в сессии с агентом. Причина: входящие — единственная папка, которую автор просматривает регулярно, поэтому она же и точка приёмки агентской работы; заметка, созданная сразу в целевой папке, уходит из поля зрения неотревьюенной.

### Как заметка во входящих помечает свой маршрут

1. **Структурный тег ставим финальный** — по `tags.md` (там каноническая таблица «тег → целевая папка»). При переносе тег не меняется.
2. **Добавляем `#review`** — маркер «агент создал, автор ещё не смотрел». Снимается при обработке (см. «Обработка входящих заметок»).
3. **`ai_generated: true`** — по политике в `note-types-frontmatter.md`, если содержимое сгенерировал скилл.
4. **Связи расставляем сразу и полностью** — `up`, `down`, `sources`, `other`, ссылки в тексте и в родительской MOC: wikilinks резолвятся по имени файла, перемещение из входящих ничего не ломает.

Пара «финальный структурный тег + `#review` в `00. Входящие/`» и есть заявка на маршрут: `obsidian-refactor-inbox` читает тег и переносит файл, не переизобретая тип заметки.

### Что во входящие не кладём

- **Журнальные заметки** (`#journal/*`) — путь семантический, выводится из даты (см. `vault-struct.md`). Создаём сразу по месту.
- **Системные артефакты** — canvas, `.base`-файлы, шаблоны, статика. Это не заметки, ревью им не нужен.
- **Правки существующих заметок** — заметка в PARA остаётся на месте. Правило про создание, не про перемещение.
- **Явное указание пользователя** («положи сразу в Карты», «создай в проекте X») перебивает дефолт.

### Отчёт после создания

В сводке (шаг 4 протокола) показывай и текущее место, и будущее:

```
📄 «Ретраи без backoff превращают деградацию в катастрофу»
   → 00. Входящие/  (#thought #review → 03. Ресурсы/04. Заметки/)
```

### Где применяется

`obsidian-ingest`, `obsidian-split-note`, `obsidian-untangle-knot`, `obsidian-note-critic`, Query → File-back, ручное создание заметок через ассистента. Обратная сторона правила — `obsidian-refactor-inbox`: он забирает заметки **из** входящих. `obsidian-enrich-note`, `obsidian-add-summary`, `book-highlights-processor` новых файлов не создают — правило их не касается.

## Рефакторинг заметок

**Лёгкий (без явного запроса):** опечатки и грамматика; недостающие заголовки; перегруппировка абзацев по смыслу; «стена текста» → списки, где уместно; недостающий frontmatter по шаблону типа.

**Средний (предложи, выполняй по подтверждению):** разделение большой заметки на атомарные; создание MOC для разросшейся темы; перемещение между папками PARA; добавление Bases-/Dataview-запросов; переименование заметки (требует обновления backlinks).

**Тяжёлый (только по явному запросу):** массовое переименование тегов; изменение структуры frontmatter по всему хранилищу; удаление заметок или больших блоков текста; массовая архивация (пачка заметок, тема или папка целиком); изменение Bases-/Dataview-запросов.

### Структурирование «грязной» заметки

1. **Организуй** — расставь заголовки, выдели списки
2. **Суммаризуй** — добавь `## Сводка` или `## Итоги` в начало
3. Выдели **вопросы** в `## Вопросы` и **действия** в `## Действия`
4. Предложи **выделить** атомарные заметки для переиспользуемых идей
5. **Свяжи** с проектами и MOC через wikilinks
6. Выяви **противоречия** и зафиксируй двумя способами: callout `> [!warning] Противоречие: …` в тексте + взаимная ссылка в `contradicts` обеих заметок (см. `note-types-frontmatter.md`)

## Обработка входящих заметок (Inbox)

Во входящих лежат две разные вещи: черновики автора (от руки, без frontmatter) и заметки агента (полный frontmatter, `#review`, `ai_generated: true`). Первым нужна полная обработка, вторым — ревью автором и переезд по уже проставленному структурному тегу.

1. Заметки из `00. Входящие/` — необработанный inbox
2. Определи тип. Если структурный тег уже стоит — тип определён, не переизобретай его
3. Добавь frontmatter по соответствующему шаблону
4. Перемести в правильную папку PARA (таблица — `tags.md`)
5. Свяжи с существующими заметками и MOC
6. Убери тег `#review` после обработки
7. Утратившее актуальность не удаляй — архивируй (следующий раздел)

## Архивирование

Полное правило — навык `/vault-archiving`. Три вещи, которые нарушаются чаще всего:

- **Заметки не удаляются** — устаревшее переезжает в `04. Архив/` с тегом `#archive`, ссылки и связи остаются нетронутыми.
- **Архив для агента плоский.** Файлы кладём в корень `04. Архив/`. Подпапку под группу переносимых заметок не создаём никогда — `mkdir` в архиве агент не делает вообще. Существующие папки там завёл автор, перенеся рабочие директории целиком; писать в них — только по прямому указанию.
- **Массовая архивация — тяжёлый рефакторинг:** явный запрос автора плюс протокол «план → подтверждение → действие».

## Ингест внешнего источника

Когда пользователь просит обработать внешний источник (статья, книга, видео, транскрипт):

1. **Прочитай источник** полностью
2. **Создай литературную заметку** в `00. Входящие/` по шаблону `Шаблон литературной цитаты.md`, теги `#literature-note` + `#review`
3. **Заполни `sources`** — название и ссылка на источник
4. **Заполни `category`** — wikilink на существующую карту/топик (приоритет — более общая) или заглушку, никогда plain text (политика — `note-types-frontmatter.md`)
5. **Выдели концепты** — для каждой идеи проверь, есть ли уже заметка. Есть — обнови на месте; нет — создай атомарку в `00. Входящие/` с `#thought`/`#concept` + `#review`
6. **Обнови существующие заметки, которых источник реально касается** — добавь источник в `sources`, уточни формулировки, повысь `confidence` при подтверждении, при противоречии — callout + `contradicts`. Ноль затронутых — нормальный результат
7. **Расставь ссылки** в обе стороны: литературная заметка → концепты, концепты → `up` на литературную заметку
8. **Установи `confidence`** — `medium` если источник один, `high` если идея подтверждается другими заметками
9. **Обнови MOC** — если концепт относится к существующей карте, добавь туда ссылку
10. **Зафиксируй противоречия** — callout `> [!warning] Противоречие: … потому что …` в тексте + wikilink в `contradicts` обеих заметок (двусторонне)

## Создание или обновление MOC

Собери все заметки по теме (теги, ссылки, папки) → создай MOC по `Шаблон карты.md` (новую — в `00. Входящие/` с `#MapOfContent` + `#review`, существующую обновляй на месте) → аннотируй каждую ссылку → добавь Bases-запрос для автообновления → свяжи с родительскими и дочерними темами. Структура и правила — навык `/knowledge-structures`.

---

## Структурирование проекта или сферы жизни

Убедись, что есть центральная заметка с целями, статусом и ссылками → сгруппируй поддерживающие заметки (ресурсы, встречи, идеи) → свяжи всё через центральную заметку → используй frontmatter `up`/`down`/`other` для навигации.

## Сохранение ответа в базу (Query → File-back)

Если в ходе разговора дан развёрнутый анализ, сравнение или инсайт — предложи сохранить его как заметку. Файл создаём в `00. Входящие/` с `#review`; структурный тег определяет будущую папку: атомарная мысль → `#thought`/`#concept`, синтез → `#synthesis`. Если пользователь скопировал ответ в `00. Входящие/` сам — обработай по стандартному Ingest.

## Проверка базы знаний (Lint / Health check)

Запускается по явному запросу: «проверь базу», «lint», «health check».

0. **Битый frontmatter** — первым делом `ruby .agents/scripts/check_frontmatter.rb .` Скрипт парсит frontmatter всех заметок и печатает те, где YAML не разбирается, с номером строки и виновником. Такие заметки Obsidian показывает с ошибкой свойств и не отображает нормально целиком. Типовые причины: незакавыченное двоеточие в `summary` или другом строковом поле, склеенные в одну строку поля, элемент списка на нулевом отступе. Шаблоны Templater скрипт пропускает — до подстановки `<% %>` они и не обязаны быть валидным YAML. Ноль на выходе обязателен, прежде чем идти дальше по чеклисту.
1. **Заметки-сироты** — ищи заметки без входящих ссылок (backlinks = 0). Предложи добавить в подходящую MOC
2. **Устаревшие заметки** — заметки со статусом `WIP` и `deadline` в прошлом. Предложи обновить статус
3. **Незавершённые секции** — заметки, где есть `## TODO` или пустые разделы
4. **Низкая достоверность** — заметки с `confidence: low`, которые можно укрепить дополнительными ссылками
5. **Дубликаты** — заметки с похожими названиями или содержанием. Предложи объединить
6. **Противоречия** — концепты, которые утверждают противоположное в разных заметках. Сначала ищи по полю `contradicts` (быстрый запрос по графу), затем по callout `> [!warning]` в текстах. Где двусторонняя связь односторонняя — почини. Где противоречие зафиксировано только в тексте — пропиши и в `contradicts`. Где конфликт давно открыт — предложи создать синтез-заметку
7. **Заметки без источника** — `ai_generated: true` с пустым `sources`: утверждение есть, а автора у него нет ни в лице пользователя, ни в лице источника. Восстанови источник (заметка-источник, URL, дневник, артефакт хранилища, файл `../rules/*`) или пометь заметку как справочную заглушку под битые ссылки. См. политику `sources` для `ai_generated` в `note-types-frontmatter.md`. Быстрый запрос (через `find -print0`, потому что имена файлов в хранилище содержат пробелы, а некоторые начинаются с `--` и ломают `xargs grep`): `find . -name "*.md" -print0 | while IFS= read -r -d '' f; do grep -q "^ai_generated: true" "$f" && grep -q "^sources: \[\]" "$f" && echo "$f"; done`
8. **Плотность агентских заметок** — `python3 .agents/scripts/check_note_density.py .` Скрипт проходит заметки с `ai_generated: true` и печатает объём против авторского корпуса, пустые секции шаблона, вводные обороты, эхо `summary` и дубли связей (`note-density.md`). Заметки, вылетевшие за верхний порог, разбирай как кандидатов в `obsidian-split-note`, а не сокращай формально
9. **Отчёт** — кратко: что нашлось, что исправлено автоматически, что требует решения пользователя

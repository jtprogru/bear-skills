# User Story и Acceptance Criteria

Файл: `<feature>_user-story.md` · Владелец: product-owner

## Назначение

Фиксирует, какую ценность и для какого сегмента пользователей создаёт инициатива, в виде историй с проверяемыми критериями приемки. Все истории инициативы живут в одном файле. Из него business-analyst берёт ID для BRD и Use Case, а system-analyst выводит из критериев `FR` и сценарии API.

## Входы

- `<feature>_business-case.md` и `<feature>_roadmap.md`: бизнес-цели `BG-n` и метрики, к которым привязывается история.
- `<feature>_backlog-priority.md`: приоритет истории.
- `<feature>_brd.md`, `<feature>_process-to-be.md`, `<feature>_use-case.md`, если они уже есть: правила, шаги и исключения, которые должны появиться в критериях.
- `<feature>_stakeholder-map.md`: кто согласует истории.

Данные от пользователя, которые запрашиваются одним сообщением до написания историй:

1. Сегменты пользователей: кто именно, в какой ситуации, что мешает сейчас.
2. Бизнес-цель или метрика, на которую влияет инициатива.
3. Baseline и target метрики успеха, срок измерения.
4. Границы: что входит в инициативу, что сознательно откладывается.
5. Известные ограничения: регуляторные, сроки, зависимые команды и системы.
6. Ключи задач в трекере, если истории уже заведены.
7. Ссылки на макеты, если у истории есть UI.

Каждый ответ, которого нет, становится `[GAP]` в том месте истории, где нужен факт. Адресаты: сегменты, ценность и метрики → пользователь; применимость норм → комплаенс; выполнимость и оценка → system-analyst; правила и шаги процесса → business-analyst.

## Правила

1. Роль в истории — сегмент с признаком, по которому его можно отличить: тип клиента, канал, ситуация, продукт. Сегмент берётся из источников; если его нет, в истории стоит `[GAP: сегмент → пользователь]`.
2. Одна история несёт одну ценность: в «я хочу» одно действие, в «чтобы» один результат. История с двумя действиями или двумя результатами делится на две.
3. «Чтобы» описывает результат для сегмента или бизнеса: сэкономленное время, полученную услугу, снижение ошибки.
4. AC описывают поведение, которое наблюдают пользователь или внешняя система: что видно на экране, какое уведомление приходит, какой статус получает операция. Реализацию описывает system-analyst в `<feature>_backend.md`.
5. У каждой истории есть минимум один позитивный и один негативный сценарий. Для каждой границы в истории (сумма, срок, количество, статус, возраст) есть сценарии на значение ровно на границе и сразу за ней.
6. Один AC — один сценарий Gherkin с одним `When`. Ключевые слова Given, When, Then, And, But английские, текст после них русский, строки внутри ячейки разделяются `<br>`.
7. Лимиты, сроки, пороги, baseline и target берутся из источников. Недостающее число записывается `[GAP]` прямо в сценарии или в ячейке метрики.
8. История, которая не проходит Small, делится по шагу процесса, сегменту, варианту данных, каналу или правилу. Новые истории получают следующие свободные `US-n`, а в разделе «Не входит в историю» исходной истории перечислены их ID и признак деления.
9. Регуляторное ограничение (152-ФЗ, 161-ФЗ, 218-ФЗ, 353-ФЗ, 115-ФЗ, требования Банка России) записывается в «Контекст и проблема» как ограничение. Его применимость к истории подтверждается вопросом `Q-n` к комплаенсу.
10. Статус `ready` получает история, у которой отмечены все пункты Definition of Ready; остальные истории остаются в `draft`.
11. Номер AC сквозной внутри своей истории: новый критерий получает следующий номер `m`, удалённый зачёркивается по правилам SKILL.md.

## Чеклист качества

- [ ] Каждая история оформлена заголовком `### US-<n>: <название>` и есть в сводной таблице с тем же названием и статусом.
- [ ] В каждой истории роль — сегмент с отличительным признаком.
- [ ] В каждой истории одно действие в «я хочу» и один результат в «чтобы».
- [ ] Каждая история ссылается на `BG-n`, который существует в каталоге, или содержит `[GAP]` вместо него.
- [ ] У каждой истории есть минимум один позитивный и один негативный AC.
- [ ] Для каждой границы, упомянутой в истории, есть AC на значение на границе и за ней.
- [ ] Каждый AC содержит ровно один `When` и наблюдаемый результат в `Then`.
- [ ] Каждый AC описывает поведение без таблиц БД, endpoint и архитектурных решений.
- [ ] Каждое число в AC и метриках имеет источник или помечено `[GAP]`.
- [ ] Метрика успеха содержит baseline, target и срок измерения, пустые поля помечены `[GAP]`.
- [ ] Таблица INVEST заполнена по всем шести буквам с обоснованием.
- [ ] Статус `ready` стоит только у историй с полностью отмеченным Definition of Ready.
- [ ] Для каждой разделённой истории перечислены новые `US-n` и признак деления.
- [ ] Каждый `[GAP]` продублирован вопросом `Q-n` с адресатом.
- [ ] Регуляторные ограничения подтверждены источником или вынесены в `Q-n` к комплаенсу.

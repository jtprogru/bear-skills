# Ревью качества артефакта

Файл отчёта: `reports/<имя проверяемого файла без расширения>_quality-review.md`, при ревью всей инициативы `reports/<feature>_quality-review.md` · Проводит: агент, которого попросили о ревью

## Назначение

Отвечает на вопрос «можно ли передавать артефакт дальше и что исправить до передачи». Ревью проводится по прямой просьбе пользователя или вызывающего агента. Ревьюер пишет только отчёт, исправления в проверяемый артефакт вносит его владелец.

## Входы

- Проверяемый файл и его reference из таблицы владельцев в `SKILL.md`.
- Артефакты каталога `<feature>`, на которые проверяемый файл ссылается по ID, и артефакты, которые ссылаются на него.
- Прошлый отчёт `reports/<тот же файл>_quality-review.md`, если он есть: повторное ревью сверяет, какие `QR` закрыты.

## Порядок

1. Определи тип артефакта и прочитай его reference.
2. Пройди каждый пункт «Чеклиста качества» из reference и зафиксируй для него «выполнен» или «нарушен» с местом в файле. Шаг завершён, когда у каждого пункта есть результат.
3. Проверь согласованность с другими артефактами — только те связи, для которых оба артефакта существуют:
   - каждый ID, на который ссылается артефакт, существует в указанном файле;
   - имена сущностей, полей, типов, статусов и кодов ошибок совпадают между backend, ERD/DDL, OpenAPI, AsyncAPI и Sequence;
   - у каждой `US` есть хотя бы один `AC`, у каждого `FR` есть источник `US`, `UC` или `BR`;
   - каждый `BR` типа «ожидание качества» покрыт хотя бы одним `NFR`, и этот `NFR` ссылается на него.
4. Для YAML- и PlantUML-артефактов запусти валидатор, если он установлен локально и у тебя есть доступ к shell: `redocly lint <файл>`, `asyncapi validate <файл>`, `plantuml -checkonly <файл>`. Когда валидатора или доступа нет, запиши в раздел «Не проверено» команду для ручного запуска: `npx @redocly/cli lint <файл>`, `npx @asyncapi/cli validate <файл>`.
5. Назначь каждому нарушению severity по таблице ниже и запиши отчёт по шаблону.

## Severity и вердикт

| Severity | Критерий |
|---|---|
| `blocker` | Передавать нельзя: противоречие внутри артефакта или с другим артефактом, отсутствует обязательный раздел, спецификация невалидна, требование нельзя проверить, требование допускает две разные реализации. |
| `major` | Передать можно, но высок риск переделки: неполные альтернативные сценарии или обработка ошибок, `[GAP]` в месте, от которого зависит разработка, ссылка на несуществующий ID. |
| `minor` | Оформление и удобство чтения: формат ID и метаданных, ссылка без имени файла, опечатки, неединообразные термины без влияния на смысл. |

Вердикт определяется максимальной severity: есть `blocker` — «не готов»; есть `major` — «готов после исправлений»; остальное — «готов к передаче».

## Шаблон отчёта

```markdown
# Ревью качества: `<файл>`

| Поле | Значение |
|---|---|
| Feature | `<feature>` |
| Проверенный файл | `<путь>`, версия <версия артефакта> |
| Reference | `references/<файл reference>` |
| Ревьюер | <агент> |
| Дата | <YYYY-MM-DD> |

## Итог

Вердикт: <не готов | готов после исправлений | готов к передаче>

Пунктов чеклиста: <N>, нарушено: <M> (blocker <x>, major <y>, minor <z>). Межартефактных несоответствий: <K>.

## Нарушения чеклиста

| ID | Severity | Пункт чеклиста | Где | Проблема | Как исправить |
|---|---|---|---|---|---|
| QR-<n> | <severity> | <текст пункта> | `<файл>:<строка>` или <раздел> | <что не так> | <конкретная правка или Q-n> |

## Межартефактные несоответствия

| ID | Severity | Артефакты | Несоответствие | Кто исправляет |
|---|---|---|---|---|
| QR-<n> | <severity> | `<файл A>` ↔ `<файл B>` | <что расходится> | <агент> |

## Статус замечаний прошлого ревью

<QR-n: закрыто | не закрыто — или «Не применимо: первое ревью»>

## Не проверено

<пункт или проверка — причина — команда или вопрос Q-n, который это закроет>
```

## Правила

1. Таблицы нарушений содержат только нарушенные пункты; выполненные входят в счётчик в «Итоге».
2. «Где» указывает строку или раздел так, чтобы владелец нашёл место без поиска.
3. «Как исправить» — правка, которую владелец внесёт без дополнительных вопросов. Если для правки нужен факт, в ячейке стоит `Q-n` с адресатом.
4. Повторное ревью перезаписывает отчёт, сохраняет номера незакрытых `QR` и заполняет «Статус замечаний прошлого ревью».

## Чеклист качества отчёта

- [ ] У каждого пункта чеклиста reference есть результат: он в таблице нарушений или учтён в счётчике.
- [ ] У каждого нарушения есть severity, место и правка или `Q-n`.
- [ ] Вердикт соответствует максимальной severity.
- [ ] Межартефактные проверки выполнены для всех существующих связанных артефактов.
- [ ] Проверяемый артефакт не изменён.

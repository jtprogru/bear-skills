# Нефункциональные требования

Файл: `<feature>_nfr.md` · Владелец: system-analyst

## Назначение

Переводит ожидания бизнеса к скорости, надёжности, защите и эксплуатации в измеримые требования с порогом, условиями и способом проверки. По NFR команда выбирает архитектурные решения, настраивает мониторинг и нагрузочные тесты, а приёмка проверяет результат. Читатели — разработчики, SRE, QA, security-reviewer.

## Входы

Прочитай в каталоге `<feature>`:

- `_brd.md` — `BR` типа «ожидание качества», ограничения, нормы;
- `_backend.md` — операции, интеграции, аудит, транзакции;
- `_openapi.yaml` и `_asyncapi.yaml` — операции и топики, к которым привязываются метрики;
- `reports/*_security-review.md` — замечания `SEC`, которые требуют NFR;
- существующие SLO, дашборды и NFR проекта — принятые метрики и окна измерения.

Факты, которые нужны до начала работы, запрашиваются одним списком:

1. Средняя и пиковая нагрузка по операциям и ожидаемый рост на горизонте планирования.
2. Целевые латентность и доступность для критичных операций.
3. Окна обслуживания и допустимый простой.
4. RTO и RPO.
5. Сроки хранения по классам данных и журналов.
6. Нормы, которые задают требования к надёжности, аудиту и хранению.
7. Окружение, на котором измеряются пороги.
8. Ограничения стека, инфраструктуры и лицензий.

`[GAP]` ставится в колонке «Метрика и порог» или «Условия измерения» той строки, которой не хватает факта. Адресаты: пороги и нагрузка → product-owner или владелец сервиса; RTO, RPO и окна обслуживания → владелец сервиса и SRE через пользователя; сроки хранения и нормы → business-analyst и security-reviewer.

## Правила

Раздел «Требования» проходит все категории таблицы:

| Категория | Что задаёт требование | Метрики |
|---|---|---|
| Производительность | время отклика и пропускная способность операций | p95 и p99 латентности в мс при заданном RPS, RPS на пике |
| Масштабируемость | рост нагрузки и данных без деградации | целевой RPS и объём данных на горизонте, способ масштабирования |
| Доступность и надёжность | SLO, окно измерения, error budget, восстановление | доступность в % за окно, error budget, RTO, RPO |
| Безопасность | связь с требованиями ИБ | ссылки на `SEC-n` и требования ИБ по ID |
| Аудит и журналирование | состав, срок хранения и защита журналов | срок хранения, задержка доставки событий аудита |
| Наблюдаемость | метрики, логи, трейсы, алерты | набор метрик, доля трассируемых запросов, алерты на нарушение SLO |
| Совместимость и интеграции | версии протоколов, обратная совместимость API и событий | период поддержки предыдущей версии |
| Сопровождаемость | развёртывание, конфигурация, откат | время отката, развёртывание без простоя |
| Соответствие нормам | обязательные требования регуляторов | норма и проверяемый критерий |
| Данные | сроки хранения, архивирование, удаление | срок хранения по классу данных, срок удаления по запросу |
| Ограничения | стек, инфраструктура, лицензии | перечень ограничений из источников |

1. Каждая категория имеет хотя бы одно требование или строку в «Не входит» с причиной.
2. Каждое требование содержит метрику, оператор сравнения, число, единицу, условия измерения и способ проверки.
3. Латентность задаётся перцентилями p95 и p99 при названной нагрузке и окне измерения; среднее значение приводится только вместе с перцентилями.
4. Доступность задаётся в процентах за окно измерения с определением успешного запроса; error budget равен разнице между 100% и SLO за то же окно.
5. Для каждой операции с финансовым эффектом или критичной для непрерывности услуги заданы RTO и RPO.
6. Каждое `BR` типа «ожидание качества» есть в разделе 3 и покрыто хотя бы одним `NFR`, который ссылается на него в колонке «Источник».
7. Число в пороге берётся из источника. Строка без подтверждённого порога остаётся в таблице с `[GAP: порог → product-owner или владелец сервиса]` в колонке «Метрика и порог».
8. Требования безопасности ссылаются на `SEC-n` и требования ИБ по ID, формулировка контроля живёт в исходном документе.
9. Одно требование содержит одну метрику; составное ожидание разбивается на несколько `NFR`.
10. Способ проверки назван так, чтобы команда могла его выполнить: нагрузочный тест с профилем, дашборд или алерт мониторинга, аудит конфигурации, ревью.
11. Приоритет задаётся по MoSCoW; требования из норм и явных ожиданий бизнеса получают `Must`.
12. Сроки хранения данных и журналов совпадают с BRD и retention топиков в AsyncAPI.

## Чеклист качества

- [ ] Каждая категория покрыта требованием или строкой «Не входит» с причиной.
- [ ] У каждого `NFR` заполнены все восемь колонок.
- [ ] Каждый порог содержит число и единицу или `[GAP]` с адресатом.
- [ ] Латентность задана перцентилями при названной нагрузке и окне.
- [ ] Доступность задана в процентах за окно с определением успешного запроса.
- [ ] Для операций с финансовым эффектом и критичных для непрерывности заданы RTO и RPO.
- [ ] Каждое `BR` типа «ожидание качества» есть в разделе 3 и покрыто `NFR`.
- [ ] У каждого `NFR` есть источник.
- [ ] Требования безопасности ссылаются на `SEC` или требования ИБ по ID.
- [ ] Сроки хранения совпадают с BRD и retention в AsyncAPI.
- [ ] В каждой строке одна метрика.
- [ ] Способ проверки каждого требования назван конкретно.

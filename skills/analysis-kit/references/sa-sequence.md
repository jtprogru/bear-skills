# Sequence-диаграмма

Файл: `<feature>_sequence.plantuml` · Владелец: system-analyst

## Назначение

Показывает порядок взаимодействия участников в каждом сценарии: вызовы API, публикацию событий, обращения к хранилищам и внешним системам, ветки ошибок и таймаутов. Диаграмма визуализирует backend-логику и связывает её с OpenAPI и AsyncAPI через подписи сообщений. Читатели — разработчики, QA, security-reviewer.

## Входы

Прочитай в каталоге `<feature>`:

- `_backend.md` — участники, сценарии, альтернативные и исключительные потоки, коды ошибок, таймауты, ретраи, идемпотентность;
- `_use-case.md` — перечень `UC`, для которых нужны диаграммы;
- `_openapi.yaml` — методы, пути, `operationId`, статусы ответов;
- `_asyncapi.yaml` — адреса каналов и имена сообщений.

Факты, которые нужны до начала работы, запрашиваются одним списком:

1. Порядок вызовов между сервисами в каждом сценарии.
2. Синхронное или асинхронное взаимодействие для каждой пары участников.
3. Где проверяется аутентификация пользователя: шлюз или сервис.
4. Способ аутентификации межсервисных вызовов и вызовов внешних систем.

Sequence строится после backend-логики: взаимодействие, которого в ней нет, сначала добавляется в `_backend.md`. `[GAP]` ставится в `note` у сообщения, которому не хватает факта: `note right of <alias> : [GAP: … → …]`. Адресаты: внешние системы → пользователь; аутентификация → пользователь и security-reviewer.

## Шаблон

```plantuml
@startuml <feature>_sequence_<uc-id>
' Feature: <feature> · Сценарий: <UC-n>
' Владелец: system-analyst · Статус: <draft | review> · Версия: <версия> · Обновлён: <YYYY-MM-DD>
' Связанные артефакты: <feature>_backend.md, <feature>_openapi.yaml, <feature>_asyncapi.yaml

title <UC-n>: <название сценария>
autonumber

actor "<Роль пользователя>" as <user_alias>
boundary "<Клиентское приложение или шлюз>" as <gateway_alias>
control "<Сервис инициативы>" as <service_alias>
database "<Хранилище>" as <db_alias>
queue "<Брокер>" as <queue_alias>
participant "<Внешняя система>" as <ext_alias>

<user_alias> -> <gateway_alias> : <действие пользователя>
<gateway_alias> -> <service_alias> : <METHOD> <path> (<operationId>), <способ аутентификации>
activate <service_alias>

alt <отказ в авторизации>
  <service_alias> --> <gateway_alias> : <401 или 403> <ERROR_CODE>
else <запрос не прошёл валидацию или бизнес-правило>
  <service_alias> --> <gateway_alias> : <4xx> <ERROR_CODE>
else <запрос корректен>
  <service_alias> -> <db_alias> : <чтение или изменение>
  <db_alias> --> <service_alias> : <результат>
  <service_alias> -> <ext_alias> : <операция внешней системы>, <способ аутентификации>
  note right of <service_alias> : Таймаут <мс>, ретраи <число> с <backoff>, ключ идемпотентности <ключ>
  alt <таймаут или ошибка внешней системы>
    <service_alias> --> <gateway_alias> : <5xx> <ERROR_CODE>
  else <ответ получен>
    <ext_alias> --> <service_alias> : <результат>
    <service_alias> ->> <queue_alias> : <channel address>: <MessageName>
    <service_alias> --> <gateway_alias> : <2xx> <тело ответа>
  end
end
deactivate <service_alias>

<gateway_alias> --> <user_alias> : <результат для пользователя>
@enduml
```

## Правила

1. На каждый `UC` из backend-логики приходится отдельная диаграмма `@startuml <feature>_sequence_<uc-id> … @enduml`; все диаграммы инициативы лежат в одном файле подряд, у каждой свой `title` с ID сценария.
2. Имена участников совпадают с таблицей «Акторы и системы» backend-логики. Стереотип выбирается по типу: `actor` — человек, `boundary` — клиентское приложение или шлюз, `control` — сервис инициативы, `database` — хранилище, `queue` — брокер, `participant` — внешняя система.
3. Синхронный вызов обозначается `->`, асинхронная отправка — `->>`, ответ — `-->`. На каждый синхронный вызов есть ответ или ветка ошибки.
4. Подпись REST-вызова — `<METHOD> <path> (<operationId>)`, как в OpenAPI. Подпись события — `<address>: <MessageName>`, как в AsyncAPI. Подпись вызова внешней системы — операция из раздела «Интеграции» backend-логики.
5. Каждый исключительный поток backend-логики для сценария представлен веткой `alt`/`else` с тем же кодом ошибки. Отказ в авторизации показан в каждом сценарии с авторизацией, таймаут — в каждом сценарии с внешним вызовом.
6. `opt` оформляет необязательный шаг, `loop` — повторы и пакетную обработку с условием выхода в заголовке, `group` — логическую группу шагов без условия, например одну транзакцию.
7. Таймауты, ретраи и ключи идемпотентности записываются в `note` у соответствующего вызова значениями из backend-логики.
8. Каждое сообщение через границу доверия показывает способ аутентификации вызывающей стороны в подписи или в `note`.
9. Подписи сообщений содержат имена полей и классы данных; конкретные значения полей остаются в примерах OpenAPI и AsyncAPI.
10. Шаги нумеруются `autonumber`; ссылка на шаг из других документов имеет вид `<UC-n>, шаг <номер>`.

## Валидация

```bash
command -v plantuml && plantuml -checkonly <feature>_sequence.plantuml
```

Без локального PlantUML: `brew install plantuml` или `java -jar plantuml.jar -checkonly <feature>_sequence.plantuml` с jar из https://github.com/plantuml/plantuml/releases. Если запуск недоступен, команда уходит пользователю в блоке «Передача».

## Чеклист качества

- [ ] Для каждого `UC` backend-логики есть диаграмма с `title`, содержащим ID сценария.
- [ ] Имена участников совпадают с таблицей «Акторы и системы» backend-логики.
- [ ] Каждый REST-вызов подписан методом, путём и `operationId`, которые есть в OpenAPI.
- [ ] Каждое событие подписано адресом канала и именем сообщения, которые есть в AsyncAPI.
- [ ] Каждый исключительный поток сценария представлен веткой `alt`/`else` с тем же кодом ошибки.
- [ ] Отказ в авторизации и таймаут внешней системы показаны во всех сценариях, где они возможны.
- [ ] Стрелки `->`, `->>` и `-->` соответствуют синхронному вызову, асинхронной отправке и ответу.
- [ ] Значения таймаутов, ретраев и ключей идемпотентности в `note` совпадают с backend-логикой.
- [ ] На каждом сообщении через границу доверия виден способ аутентификации.
- [ ] Каждое взаимодействие на диаграмме описано в backend-логике.
- [ ] `plantuml -checkonly` проходит без ошибок, или команда проверки передана пользователю.

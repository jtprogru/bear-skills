# Section-by-section guide: filling a postmortem from session context

Загружай этот файл, когда дошёл до шага 6 в SKILL.md и нужно конкретное руководство по тому, как заполнить отдельные секции постмортема. Здесь — по одной секции; читай только нужное.

Главный принцип: постмортем — это **разбор задним числом** (что объективно произошло, почему, что менять). Данные берутся из текущего диалога: что пользователь рассказал, какие факты вы вместе зафиксировали в ходе сессии, что видно в логах/коммитах. Если факта в сессии нет — спрашивай у пользователя или ставь GAP-маркер. Не выдумывай.

---

## TL;DR / Summary

Цель: 2-3 предложения, после которых читатель решает, читать ли дальше.

Структура: «[краткое описание симптома и масштаба]. Корневая причина — [одна фраза]. Mitigation — [одна фраза]. Главный системный урок — [одна фраза].»

Пример:

> 2026-06-03 в 11:25 UTC продуктовая разработка сообщила о зависании создания 50 ГБ дисков при создании ВМ; затронуты 49 PV через 40+ tenant-namespace (включая 4 DB-tier). Корневая причина — накопление 16 stale-Primary DRBD-ресурсов (все на ноде w1), блокирующих csi-provisioner ретраями DeleteVolume. Mitigation за ~3 часа: серия `drbdadm secondary` на w1 разблокировала retry-storm. Главный системный урок — отсутствует алерт на накопление `Released` PV и на «все Primary на одной ноде»; детекция произошла через жалобу, а не через монитор.

Не пиши: «случилось много всего, разбирались несколько часов, в итоге починили».

## Impact

Если шаблон проекта даёт таблицу (как `runbooks/templates/postmortem.md` у h3llo) — заполни все строки. Не оставляй пустых ячеек: ставь `<GAP — …>` или `неприменимо`.

| Поле таблицы | Что подставлять |
|---|---|
| Affected service(s) | названия сервисов, которые задеты (Kubernetes/storage/network компоненты) |
| Affected users | классы пользователей, не имена: «внутренние пользователи через продуктовую разработку», «N тенантов» |
| Контур | Prod/Stage/Dev. Если из обсуждения не ясно — спроси или GAP |
| Длительность impact | end − start (по UTC). Округляй до минут |
| SLO breached | если SLO ещё не зафиксирован в каталоге — `<GAP — SLO ... не определён, см. [53-slo-catalog.md](...)>`. Не выдумывай таргет |
| Error budget impact | если EBP не утверждена (например, ADR-0011 Proposed) — `<GAP — error budget policy не утверждена>` |

| Financial impact | для внутренних/pre-Prod — обычно «N/A (pre-Prod)». Не выдумывай суммы |

## Timeline

План:

1. **Соберись с пользователем по ключевым моментам.** Не каждое событие = строка. Что считается переломным:
   - Триггерящее событие (deploy, config change, внешний триггер).
   - Первое сообщение об инциденте (детектирующее событие).
   - Объявление инцидента (severity + назначение лида).
   - Подключение SRE / получение доступа.
   - Каждая значимая гипотеза: формулировка + подтверждение/опровержение (если важна для root cause).
   - Каждое действие mitigation: запуск + verify.
   - Точка mitigated (симптом исчез).
   - Подтверждение latency/функциональности после mitigation (например, bench-прогон).
   - Точка resolved (если есть).
2. **Все timestamps в UTC.** Если пользователь говорит в локальной TZ (MSK = `+03:00`) — конвертируй: UTC = MSK − 3ч. В заголовке таблицы — `(UTC)`.
3. **Если точного timestamp нет** — спроси пользователя. Если он сказал «не помню точно» — пиши приблизительное с пометкой `~` или GAP.
4. **В колонке «Источник»** — где взято подтверждение (внутренний чат, dashboard, log, bench CSV, commit, сессия). Это нужно, чтобы action items потом ссылались на конкретный артефакт.
5. **Цель — 10-20 строк.** Если получилось 50 — слишком гранулярно. Если 5 — слишком грубо.

Пример (фрагмент):

| Время (UTC) | Событие | Источник |
|---|---|---|
| 2026-06-03 11:25 | Внутренний репорт от продуктовой разработки: hang при create 50 GiB VM | внутренний чат |
| 2026-06-03 12:25 | SRE Lead запрашивает прод-доступ для участия в расследовании | внутренний чат |
| 2026-06-03 12:35 | Инцидент объявлен SEV-2 ретроспективно | сессия |
| 2026-06-03 13:00 | Дамп PV: 49 в Released, гипотеза «массовая zombie-аккумуляция» подтверждена | `/tmp/zombie-pv.txt` |
| 2026-06-03 13:55 | Dry-run zombie-cleanup скрипта | `/tmp/zombie-cleanup-…log` |
| 2026-06-03 14:25 | План mitigation: упрощённая процедура (только `drbdadm secondary` на Primary) | сессия |
| 2026-06-03 15:10 | Batch demote на 13 PV: все Primary на w1 (KEY FINDING) | сессия |
| 2026-06-03 15:30 | Verify: 16/16 zombie ушли, retry-storm схлопнулся 10+ → 1 PVC. Статус → mitigated | сессия |

## Root cause

Раздели на 2-3 уровня:

### Непосредственный технический фактор

Что конкретно ломало пользовательский флоу. Одна-две формулировки, не пересказ.

Пример: «csi-provisioner был заблокирован retry-loop'ом на 10+ PVC, у которых DRBD-resource на ноде `pub-wl-w1` оставался в `Usage=InUse, role:Primary` после удаления PVC в Kubernetes. LINSTOR держал `DeleteVolume` в очереди, csi-provisioner выжигал gRPC deadline, новые `CreateVolume` стояли в той же очереди — отсюда наблюдаемый hang при create 50 GiB VM.»

Если непосредственная причина не до конца ясна — пометь как `<гипотеза, не подтверждена>`. Не объявляй преждевременно.

### Contributing factors (системные)

Что позволило непосредственной причине существовать или быть незамеченной. Эти пункты — кандидаты в action items.

Пример (отсюда тащи в Action items):

- Нет алерта на накопление `Released` PV — 49 штук копились **месяцами** (возраст до 68 дней), никем не замечались.
- Нет алерта на «все Primary одного storage pool на одной ноде» — w1-bias был структурным.
- Нет runbook на «как demote stale Primary без `linstor rd delete`» — процедуру пришлось выводить ad-hoc во время инцидента.
- Нет baseline на `disk-create latency` — после mitigation непонятно, лучше ли стало (p95=77s — это много или мало?).
- Detection — через жалобу в чате, не алертом.

### Что НЕ было причиной

Это важно: фиксируем гипотезы, которые в ходе расследования были отвергнуты, чтобы команда не возвращалась к ним в будущем.

Пример: «KubeVirt/CDI не были причиной — все VMI/DV/PVC верхнего уровня были в норме. SDN (h3ovn) не вовлечён.»

## What went well

Что сработало как задумано. Не «всё было хорошо» — конкретно:

- Существующий скрипт `pvc-create-bench.sh` пригодился для подтверждения mitigation (важный артефакт — он же станет regular CI bench).
- Dry-run скрипта `zombie-pv-cleanup.sh` поймал, что слепое удаление RD небезопасно — это сэкономило большой incident.
- Гипотеза о массовой zombie-аккумуляции быстро подтвердилась через дамп PV в Released — корреляция оказалась прямой.
- Упрощение процедуры в ходе расследования (от `l rd delete` к одному `drbdadm secondary`) — это успех, а не провал; ad-hoc, но правильный.

---

## What went wrong

Что замедлило mitigation или сделало impact больше. Это сильнейшие кандидаты в action items.

- Detection через чат, не алерт — задержка от triggering event до объявления SEV-2 = ~1 час.
- Нет baseline latency — после mitigation непонятно, насколько лучше.
- SRE Lead изначально не имел прод-доступа — эскалация прав в середине инцидента.
- `Released` PV копились месяцами без алерта (max age — 68 дней) — это масштабный fail observability.

---

## Where we got lucky

Что обошлось благодаря удаче, не дизайну. Не обесценивай — это важно для honest assessment.

- Симптом не привёл к data loss — все zombie PV были именно zombie (PVC уже удалён в K8s), а не активные тома.
- DB-tier zombie оказались мелкими (WAL/config-том), не основной storage — потеря бы была болезненной.
- pre-Prod, не Prod — финансового impact'а почти нет, можно было экспериментировать с процедурой.

---

## Lessons learned

Системные выводы, обобщения. Не пересказ.

- LINSTOR scheduler может систематически биасить Primary на одну ноду — нужен monitoring distribution + явная placement policy.
- `Released` PV нельзя оставлять накапливаться — это compound state, который рано или поздно ломает control plane.
- Симптом «бесконечное создание» — это **наблюдаемое следствие** retry-storm на control plane. Алерт нужен не на симптом, а на upstream (retry rate, очередь csi-provisioner, `Released` PV count, distribution Primary по нодам).
- Detection через жалобу — антипаттерн. Каждый этот случай = action item на алерт.

## Action items

Каждый action item обязан иметь:

1. **Action** — конкретное, тестируемое («добавить алерт X с threshold Y», не «улучшить мониторинг»).
2. **Owner** — роль или команда (например, `Storage / Piraeus owner`, `SRE`, `Internal Developers`). **Никогда личное имя.**
3. **Priority** — P0/P1/P2 по легенде шаблона. P0 = без этого инцидент повторится скоро.
4. **Deadline** — конкретная дата. Если не знаешь — `<GAP — нужен дедлайн от owner-команды>`, дефолт-предложение пиши явно.
5. **Status** — Open / In progress / Done.
6. **Ссылка на тикет** — если есть. Если нет — `<GAP — тикет не открыт>`.

Источники action items:

- Всё, что в ходе сессии обозначилось как «надо сделать».
- Contributing factors из секции Root cause (каждый — кандидат в action item).
- What went wrong (каждый пункт — кандидат).

Не дублируй то же действие в нескольких строках. Группируй: «kernel-check + миграция на `io.max` если v2» — одна строка с двумя подзадачами в одном action.

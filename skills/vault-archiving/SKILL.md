# Архивирование заметок

Правило про `04. Архив/` — что туда попадает, как попадает и чего агент там не делает никогда.

## Архив для агента — плоская директория

**Агент кладёт заметки в `04. Архив/` только корнем. Подпапки под группу переносимых заметок не создаются — ни под тему, ни под источник, ни под дату, ни под «пачку из этой сессии».**

Это самое частое нарушение: агент архивирует пять заметок про один проект и заводит под них `04. Архив/Проект X/`. Так делать нельзя. Пять заметок кладутся пятью файлами в корень архива.

```bash
# правильно
mv "01. Проекты/Старый проект.md" "04. Архив/"

# неправильно — папка под группу
mkdir -p "04. Архив/Старый проект" && mv ... "04. Архив/Старый проект/"
```

**Папки в архиве появляются только тогда, когда автор лично переносит туда директорию целиком.** Существующие `Comlogic/`, `POSI/`, `Авито Тех/` — это перенесённые рабочие папки прошлых мест работы, а не результат агентской группировки. Агент кладёт файл внутрь такой папки только по прямому указанию («убери в архив папку Comlogic», «положи в `04. Архив/POSI/`»).

Почему так: архив — свалка по назначению, а не вторая база знаний. Навигация по нему идёт поиском и backlinks, а не деревом папок; папки, придуманные агентом, дают ложную структуру, которую потом никто не поддерживает. Плюс архив исключён из индекса `myvault_search` (см. `CLAUDE.md`), так что вложенность не помогает найти ничего — только мешает `rg` и `find`.

## Архивирование вместо удаления

**Заметки не удаляются.** Устаревшее, потерявшее актуальность, дубли-неудачники — переезжают в `04. Архив/`. То же с большими блоками текста: не вырезать, а переносить (принцип 2 в `CLAUDE.md`).

Порядок:

1. `mv` файла в корень `04. Архив/` (кавычки вокруг пути — имена с пробелами и кириллицей).
2. Добавить `#archive` в `tags` (структурный тег заметки при этом сохраняется — он говорит, чем заметка была).
3. Ссылки, `up`/`down`/`other`/`sources`, Dataview- и Bases-блоки оставить как есть. Wikilinks резолвятся по имени файла, переезд их не ломает.
4. Имя файла не менять. Переименование при архивации рвёт backlinks ради ничего.

Что архивация **не** отменяет: `description` у проектов остаётся обязательным и в архиве (`note-types-frontmatter.md`); `sources` не очищается никогда.

## Конфликт имён

В архиве уже лежит файл с таким же именем — не перезаписывать `mv` молча и не заводить папку, чтобы «развести». Останови и спроси: это дубль (тогда сливаем) или разные заметки (тогда автор решает, как переименовать).

## Кто и когда архивирует

- **`obsidian-refactor-inbox`** — единственный скилл, который архивирует в рабочем цикле: утратившая актуальность заметка из инбокса уходит в `04. Архив/` с `#archive`.
- **`obsidian-inbox-review`** — только помечает кандидатов в отчёте, файлы не двигает.
- **`obsidian-untangle-knot`** и перепривязка ссылок — архив не трогают вовсе: ссылки там исторические.
- **Массовая архивация** (пачка заметок, папка, тема целиком) — тяжёлый рефакторинг: только по явному запросу автора и через протокол «план → подтверждение → действие» (`workflows.md`).

## Самопроверка перед `mv`

1. Целевой путь — ровно `04. Архив/<Имя файла>.md`, без промежуточных папок?
2. Ни одного `mkdir` в архиве в этой сессии?
3. Файл с таким именем в архиве уже есть?
4. `#archive` добавлен, остальные теги и связи целы?
5. Архивация запрошена автором или входит в обработку инбокса — а не придумана по ходу?
